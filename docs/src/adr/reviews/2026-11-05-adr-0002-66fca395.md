## Prior blocker disposition

The retained historical review contains no numbered blockers, but its approval applies only to the earlier Owner-based candidate. I have not carried that approval forward.

The revised requirements are addressed independently:

1. **Nonbreaking Admin naming:** Decision 7 retains `ModifyRoles` as the actual Rust variant and canonical wire identity, while adding the Admin associated constant and serde input aliases. This avoids both Rust-import breakage and the input-only-alias trap where new clients emit values an old contract cannot decode.
2. **Single administrative capability:** Decisions 1, 2 and 4 assign role management, configuration and upgrades to the same RBAC identity. The proposed Owner component, ownership API, storage and bootstrap parameter are explicitly removed.
3. **Standard versioned state:** Decision 5 replaces the handwritten migration with `VersionedState<State>`, target version 1, a typed V0-to-V1 transformer, and `impl_versioned_state!`. It correctly distinguishes required typed migration input from the empty raw input required when already current.
4. **Retained scope:** Full configuration replacement, prospective cache semantics, configuration audit events and focused direct-WASM verification remain. Controller integration, dependency/toolchain changes and live authority changes remain excluded.

## Tradeoff assessment

**The compatibility choice is sound.** Retaining the old variant and canonical serialization preserves existing Rust imports, exhaustive matches, contract JSON, gateway JSON and schemas. New terminology is additive rather than a second persisted role. Keeping canonical outbound values also allows updated gateway tooling to address the released contract without version-dependent RPC branches.

I traced the existing receiving path: gateway requests undergo typed serde parsing, `RoleValue` converts into the common contract role, and role operations serialize that common role for the contract. There is no separate role-name dispatch registry that would silently discard the alias. Keeping aliases out of canonical schemas is an explicit discoverability tradeoff, not an overlooked runtime schema restriction.

**Admin deliberately expands authority.** Reusing the existing role avoids maintaining a second ownership lifecycle, but grants every existing role administrator configuration and arbitrary-code powers. The ADR states that expansion plainly rather than presenting it as a cosmetic rename.

**Full replacement remains coherent.** It provides a smaller administrative interface at the acknowledged cost of stale snapshots restoring unrelated settings. The consequences and recovery guidance accurately describe that risk; no merge or concurrency protection is implied.

**Framework reuse is appropriate.** The shared version mechanism already treats missing metadata as V0 and provides typed transformation, complete-chain validation and private migration routing. Moving the existing adapter rather than rebuilding collections is consistent with the preservation requirement. The record gives sufficient architectural direction without duplicating an implementation specification.

## Security and maintenance assessment

The important boundaries are explicit: exactly one yoctoNEAR for administrative calls, Admin authorization, validation before replacement, separate TrustedUpdater permissions, and preservation of historical configuration during migration.

Preserving role bytes and the `~r` namespace is essential because RBAC membership keys incorporate the Borsh-serialized role. Retaining feed prefix `a` and moving the existing adapter avoids introducing an unnecessary collection migration. Actual released-WASM preservation remains a required implementation proof, not something established by this ADR review.

Upgrade handling reuses the shared primitive for both inline WASM and immutable global hashes. Both branches append migration to the same self-receipt. The rollback claim is consistent with [NEAR’s documented receipt semantics](https://docs.near.org/protocol/transactions/transaction-execution.md#transaction-status), and the ADR correctly requires inspection of receipt failures rather than equating scheduling with completion.

The record also discloses the material operational risks: arbitrary-code authority, no timelock or code allowlist, possible loss of administration after explicitly removing the last Admin on a keyless account, and the distinction between role removal and access-key removal. Network gas feasibility and monitoring installation are appropriately left to a separately approved rollout.

The acceptance criteria cover the relevant boundaries without requiring another controller framework. Existing Owner-based implementation tests are not evidence that the revised behavior works; the ADR correctly treats revised compatibility, migration and authorization proofs as future implementation gates.

## Consequence simulations

The following are **[INFERENCE] static simulations of the specified design**, not executed tests.

1. **Old and new clients address different contract versions.**
   An old client sends `"ModifyRoles"` to the revised contract and reaches the same administrative membership. A new gateway accepts `"admin"`, converts it into the existing role value, and emits `"ModifyRoles"` to the released contract. Directly sending `"Admin"` to the old contract is not promised to work; normalization by updated tooling preserves compatibility. Keeping legacy canonical schemas also avoids changing generated clients’ outbound enum values.

2. **A released V0 deployment receives the versioned implementation.**
   Missing `__v` is interpreted as version 0. A correctly registered typed V0-to-V1 transformer reads the adapter-only root and moves its existing adapter into current state. Because it neither reconstructs the feed collection nor rewrites RBAC memberships, the specified preservation boundary includes historical configuration, collection handles, feed records and replay timestamps. Existing `ModifyRoles` members become Admins without reseeding. The ADR correctly requires proof using the actual released WASM rather than treating this source-level reasoning as sufficient.

3. **Migration arguments are wrong or stale.**
   With V0 state, malformed or incomplete migration input cannot bypass the framework’s requirement to reach target version 1. With current V1 state, `{}` is rejected because the standard no-migration path requires empty raw input. When deployment and migration share the specified self-receipt, migration failure rolls back that receipt’s code and state changes. Receipt outcomes, code identity, version and retained-state snapshots establish failure and support a corrected retry; scheduling alone does not establish success.

4. **A later complete configuration restores older settings.**
   Admin installs C1, then another authorized call based on C0 changes one field while restoring the other C0 values. That outcome is deliberately permitted by full replacement. The ADR exposes the stale-snapshot risk, requires review of complete configurations and execution order, and identifies detection through `get_config` and successful `config_updated` records. Recovery is another validated complete replacement.

5. **The last Admin is explicitly removed.**
   The ordinary last-member guard prevents accidental removal through its default path, but the preserved override permits it. On a keyless account, no Owner fallback or public bootstrap restores authority. The ADR accurately warns that recovery may be impossible; remaining deployment authority is a separate recovery capability, not something role changes create or revoke.

These scenarios have prevention, detection and recovery guidance—or explicitly acknowledge that recovery may not exist.

## Requirement coverage

**The alias requirement is met across the relevant surfaces.** Contract JSON retains `"ModifyRoles"` and accepts `"Admin"`; gateway JSON retains `"modify_roles"` and accepts `"admin"`. Legacy Rust variants remain available, Borsh role tags remain 0/1, and the manager advertises `admin` while accepting `modify-roles`. The canonical-schema tradeoff is explicit.

**The authority decision is complete.** Admin controls roles, configuration and upgrades; TrustedUpdater remains separate. Fresh construction grants both existing roles to explicit `admin_id`, not the predecessor. The proposed Owner component, APIs, storage initialization and bootstrap parameter are removed from the intended implementation.

**Versioning and preservation are adequately specified.** The target is version 1, fresh construction records it, and legacy state uses a typed transformer through the shared framework. Migration must preserve historical configuration without revalidation, feed prefix `a`, RBAC prefix `~r`, records and timestamps. Standard version views and migration-input behavior are included.

**Configuration and observability remain coherent.** Full validated replacement retains the existing signer-policy and timing domains. Policy changes are prospective, not cached-price revocation. The additive audit event carries the actual predecessor and complete applied configuration, with event-only hexadecimal signer encoding and receipt-success filtering.

**Minimal scope is maintained.** Focused direct adapter tests replace the need for controller scenarios. No DAO topology, governance integration, new gateway methods, production authority selection, live upgrade, key deletion, dependency upgrade or toolchain change is introduced.

## Alternative fairness

The alternatives are substantive and fairly presented.

Partial patches receive credit for preserving unmentioned live settings; full replacement wins on interface size while accepting stale-snapshot risk. Separate Owner authority receives credit for separating trust tiers; it is rejected because that distinction is not the chosen requirement, not because it lacks security value.

The record correctly distinguishes an input-only serde alias from full compatibility. Retaining legacy Rust and outbound identities is a justified constraint, even though “Admin” consequently remains an additive name rather than the canonical serialized spelling.

The handwritten-bootstrap and controller alternatives are also fairly bounded. The existing framework already supplies version-aware migration, while selecting a controller now would expand the decision beyond the adapter boundary.

## Security, maintenance, and verification assessment

The principal security consequence is explicit: preserved role administrators may deploy arbitrary code. Configuration validation cannot constrain an Admin who can replace the implementation, and the ADR does not imply otherwise. No timelock or code allowlist is promised.

Framework reuse avoids maintaining a second migration protocol. Preserving collection handles and role-key identity avoids unnecessary data movement. Both upgrade-source branches in the shared helper append migration to the same self-targeted promise batch, consistent with [NEAR’s receipt rollback semantics](https://docs.near.org/protocol/transactions/transaction-execution.md#transaction-status).

The verification requirements are appropriate for later implementation: authorization/deposit boundaries, aliases and canonical encodings, historical state preservation, generated migration behavior, rollback, both upgrade sources and maximum-policy event logging. Existing Owner-based tests do not prove the revised design; the record correctly requires revised coverage.

Network gas feasibility, actual memberships and external event-consumer readiness remain separately approved rollout checks. Emitting an audit event is correctly distinguished from installing monitoring.
