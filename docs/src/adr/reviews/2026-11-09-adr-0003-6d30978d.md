## Prior blocker disposition

1. **Additional attacker keys—finding 4518812865: resolved.** ADR line **133** now requires re-enumerating child keys **during recovery**, removing **every unauthorized key**, rotating Deployer, and verifying the final key list. Recovery no longer assumes the originally supplied key is the attacker’s only remaining credential.

2. **Trusted removal authority and no-trusted-key fallback: resolved.** Removal expressly requires a trusted full-access key **on that child**, if one remains. The fallback now depends on the absence of a **trusted** child key, not on the unintended key being the sole key. It therefore covers multiple attacker-controlled keys with no trusted key remaining. Where no authorized contract removal method exists, it requires stopping use of that Deployer, disclosure, and migration to a newly reviewed market where feasible.

3. **Role rotation versus child-key revocation: preserved.** The row explicitly states that Deployer rotation does not revoke child keys. It does not invent registry-Owner authority over an existing child or promise recovery of compromised funds. The keyless-market patching limitation remains explicit.

4. **API-scoped Owner authority: remains resolved.** Decision 1 limits Owner exclusivity to the contract API and retains the warning that registry full-access-key holders can replace code outside Owner and role guards.

5. **Revision-pinned evidence: remains resolved.** DAO, migration, and upgrade-solvency evidence remains linked to the immutable implementation revision above. The referenced committed sources contain the described scenarios; they are not represented as implementation in this ADR-only branch.

6. **Post-key-deletion proof: remains resolved.** Decision 6 still requires pre-deletion DAO proofs, followed by registry-key deletion, another DAO same-code upgrade, and a distinct Uploader→DAO approval→Deployer deployment without a registry signing key. Successful receipts and final key inspection remain prerequisites to alpha→v1 promotion.

## Security and maintenance assessment

The recovery model now follows the actual authority boundary. In the separate implementation, `deploy` receives `full_access_keys`, iterates them, and adds each through `add_full_access_key`; its finalization callback records deployment rather than managing those keys. Registry role changes do not revoke child-account credentials.

[NEAR’s access-key documentation](https://docs.near.org/protocol/accounts-contracts/access-keys#full-access-keys) confirms that full-access keys can add/remove keys and replace contract code. Re-enumeration and final verification are therefore necessary: removing only the originally observed key is insufficient.

The corrected fallback appropriately avoids relying on an attacker-held key merely because keys still exist. It acknowledges migration feasibility limits and retains the keyless-market limitation. No new recovery API, implementation obligation, or production action is introduced.

## Blockers

1. **[P2] Gate child-key recovery on trusted code and state**

   **File:** `docs/src/adr/0003-separate-registry-capabilities-and-uploader-funded-code-storage.md`  
   **Lines:** 133–133  
   **Confidence:** 0.93

   When the unintended child full-access key has already replaced the child’s code or patched its storage—both explicitly listed as warning signs—the trusted-key recovery branch ends after removing unauthorized keys, rotating Deployer, and checking the key list. Those actions do not undo the code or storage changes, so an operator can satisfy the stated recovery procedure while the child remains compromised. The inspected deployment consumer installs actual child full-access keys, and [NEAR documents their authority to deploy replacement code](https://docs.near.org/protocol/accounts-contracts/access-keys#full-access-keys); the separate deployment runbook also explicitly describes their storage-patching authority. **Minimum correction:** require establishing trusted child code and state before resuming use; if integrity cannot be established or safely restored, apply the disclosure/migration fallback even when a trusted child key survives. A clean key list must not be presented as sufficient recovery from an already-modified child.
