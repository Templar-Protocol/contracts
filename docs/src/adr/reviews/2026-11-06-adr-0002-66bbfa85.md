## Consequence simulations

These are source-level traces, not newly executed tests.

- **Approval needs additional payer funding:** Uploaded approval computes the retained-storage delta against the original uploader’s ledger. Insufficient available credit rejects approval rather than charging the DAO or assigning the liability to a new owner.
- **Ownership changes after approval:** Retained charges remain associated with their original payer. Removing version code releases that payer’s credit; withdrawal does not require a role.
- **A deployment or probe fails during a shortfall:** Failure callbacks remove reservations/provisional entries without invoking the solvency guard, then report failure through a separate promise.
- **A V2 global→local upgrade would consume user credit:** The post-deployment check rejects the atomic batch, restoring the previous code mode and state. The inspected solvency scenario also asserts subsequent withdrawal.
- **Deployer is compromised:** It can install a child full-access key and later replace child code. The ADR correctly identifies this broader trust boundary rather than promising immutable or exclusively DAO-controlled children.
