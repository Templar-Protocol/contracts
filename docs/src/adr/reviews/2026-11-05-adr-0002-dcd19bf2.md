## Tradeoff assessment

Full replacement is a coherent, smaller interface that follows the existing Pyth Lazer administration pattern. The ADR fairly acknowledges its principal disadvantage: an older complete snapshot can overwrite unrelated newer settings. Execution-order review and recovery through a fresh complete configuration are explicit.

Separate ownership adds an authority to administer but avoids conflating role management with configuration and arbitrary code deployment. Reusing the standard component is preferable to another ownership protocol.

Deferring DAO selection, controller policy, timelocks, and key removal is appropriate. None is necessary to decide or directly verify this adapter interface.

## Security and maintenance assessment

The important invariants are explicit and supported by the proposal: validation before replacement, unchanged configuration encoding, prospective policy changes without clearing feeds or replay timestamps, independent RBAC, and sentinel-based bootstrap that cannot reopen ownership after renunciation.

The upgrade design uses immutable code sources and batches deployment with migration in one self-receipt. Receipt-level failure inspection and target-network gas feasibility remain explicit operational obligations. The ADR correctly exposes the owner’s arbitrary-code authority, incomplete authority handover through ownership alone, and potentially irreversible loss of administration on a keyless account.

The smallest useful verification is adequately bounded: focused fast tests for authorization, validation, wire forms, state preservation and maximum-policy logging, plus direct real-WASM proofs for released-state bootstrap, rollback and both upgrade sources. These are implementation acceptance gates, not additional work required to approve this decision record. No controller framework or live-chain execution is needed for this review.

## Consequence simulations

The following are **[INFERENCE] static simulations of the specified decision**, not executed tests.

1. **An older full snapshot restores stale settings.**  
   Starting from configuration C0, one successful call installs C1. A later call based on C0 changes a different field but also restores the remaining C0 fields. Full replacement intentionally permits that outcome; signer-policy validation cannot detect stale administrative intent. The ADR explicitly describes this tradeoff, requires review of every field and execution order, and provides detection through `get_config` and successful `config_updated` records. Recovery is a fresh complete replacement through the current owner. No merge or concurrency protection is implied.

2. **A wrong bootstrap owner or renunciation loses administration.**  
   An owner-uninitialized adapter accepts one explicit bootstrap owner. Once its initialization sentinel exists, another supplied owner is rejected—even after renunciation clears the owner value. Therefore an RBAC administrator cannot repair ownership through the configuration interface or bootstrap path. The ADR accurately limits recovery to remaining authorities and separately reviewed deployment recovery before key removal; otherwise recovery may be impossible. Ownership transfer also leaves role memberships and account keys untouched, so it is not presented as complete authority handover.

3. **Deployment executes but migration fails.**  
   Inline deployment or immutable-global-code selection is followed by migration in the same self-receipt. Missing bootstrap arguments, attempted reinitialization, incompatible state, or insufficient execution resources cause that receipt to fail, rolling back its code/state changes. Scheduling success is not completion, and unrelated successful receipts are not thereby rolled back. The ADR correctly requires receipt-failure inspection and code/config/role/feed comparisons before retrying with corrected source, arguments, or budget.

Each scenario has warning signs, prevention, detection, and a recovery path—or an explicit statement that recovery may not exist.

## Alternative fairness

The alternatives are substantive and fairly represented:

- **Partial patches** receive credit for preserving unmentioned live settings. Their additional input and merge semantics are weighed against full replacement’s smaller interface and acknowledged stale-snapshot risk.
- **Reusing `ModifyRoles`** genuinely reduces authority-management complexity, but also grants role administrators configuration and arbitrary-code authority. Separate ownership preserves a meaningful capability boundary.
- **Selecting a controller now** would establish one topology, but would commit this change to an unrequested integration. Deferral is justified by scope, not by a claim that existing governance cannot call the adapter.

The chosen option does not conceal the operational cost of complete snapshots or the maintenance cost of separate authorities.

## Security, maintenance, and verification assessment

The principal security boundaries are explicit: validate before replacement; retain historical decoding compatibility; keep RBAC independent; prevent post-renunciation bootstrap; and restrict upgrade sources to inline bytes or immutable hashes. The owner’s ability to deploy arbitrary code is stated plainly, rather than obscured by configuration-validation guarantees.

The event encoding is consistent with the bounded signer policy and avoids changing existing configuration or `write_prices` wire forms. Maximum-policy logging is an explicit acceptance gate. External consumers and monitoring remain rollout obligations; emitting an event is correctly not equated with installing an alert.

Verification is sufficient **for this decision record**. Fast tests address authorization, validation, serialization, state preservation, and sentinel behavior. Direct-WASM tests address the boundaries mocked tests cannot establish: generated entrypoints, actual released-state compatibility, receipt rollback, and both upgrade sources. Historical source and artifact metadata support the release boundary but do not replace the required binary proof.

The 250-Tgas migration reservation is not presented as proof that every deployment fits target-network limits. Network feasibility and selected authorities remain separately gated before rollout. No controller integration, testnet transaction, or production action is required to approve this ADR.
