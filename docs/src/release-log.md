# Deployment and Version Log

This page records every contract build Templar has released, how to tie a deployed contract back to one of them, and which audit covers it. The release catalog is generated from [`contract/artifacts/releases/`](https://github.com/Templar-Protocol/contracts/tree/dev/contract/artifacts/releases), the reviewed, in-repository record of released WASM; CI fails if this page drifts from it. Per-market deployment records (account, version key, code hash, block height) live on chain in the [registry](./contract/registry.md).

## How to Read the Catalog

- **A release is a published build, not a deployment.** A row means a release tag was cut and its WASM built reproducibly and published as a GitHub Release asset. It does not mean those bytes run anywhere. Which markets run which version is recorded by the registry (`get_deployment` returns the version key, code hash, and block height for any deployed account).
- **Rows are immutable and appended by CI.** A new release adds a row; an existing row is never rewritten. The seventeen oldest rows predate this workflow and were recovered from the accounts running them.
- **Source runs ahead of releases.** Crate versions are bumped by every change, including dependency bumps, and most versions are never built as WASM. The newest released version of an artifact is therefore usually older than the version in `Cargo.toml` on `dev`; the summary table shows both.
- **Registry key** is the name a build is registered under for deployment: `vX.Y.Z` for market versions in `v1.tmplr.near`, and `<package>@<version>#<sha256>` for the proxy oracle and governance builds pinned by the mainnet deployment profile. **Input needed** marks rows whose key has not been confirmed against the registry's `list_versions` output.
- **Audit** names the engagement whose scope covers the build. **Input needed** marks rows where the audited commit has not been mapped to the release tag; see [Audit Coverage by Version](#audit-coverage-by-version).

## Verifying a Deployed Contract Against the Catalog

1. Read the deployment record from the registry, which includes the version key and the code hash recorded at deployment:

   ```bash
   near contract call-function as-read-only v1.tmplr.near get_deployment json-args '{"account_id": "<market-address>"}' network-config mainnet now
   ```

2. Verify the on-chain code against the source commit in its NEP-330 metadata, as described in [Contract Verification](./addresses.md#contract-verification):

   ```bash
   near contract verify deployed-at <market-address> mainnet now
   ```

3. To match the bytes to a catalog row, download the release asset from the row's release tag and compare its digest with the SHA-256 column:

   ```bash
   sha256sum templar_market_contract-1.3.0.wasm
   ```

   The catalog's byte length and SHA-256 are the pins the repository's own tooling verifies every fetched artifact against, so a matching digest establishes that the deployed bytes are the reviewed release build.

## Recording Mainnet Deployments

Templar's [security policy](https://github.com/Templar-Protocol/contracts/blob/dev/SECURITY.md) commits to recording every mainnet deployment with its version, code hash, account, and audit reference. The catalog above covers the version and code hash; the registry covers the account and deployment block. **Input needed**: a per-deployment table (market account, version key, deployment date, audit reference) is not yet generated because NEAR RPC was not reachable when this page was written. Until it is, the [registry page](./contract/registry.md) shows how to list deployments and read each one's record.
